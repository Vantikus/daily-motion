# Работа с Daily Motion в GPT

В новом чате указывайте репозиторий `Vantikus/daily-motion` и ветку `main`.
Актуальный код и документы проекта важнее пересказа старого чата. Начинайте с
AGENTS.md и README.md; для стилей дополнительно используйте CSS_GUIDE.md.

## Базовый промпт

> Работаем с Vantikus/daily-motion, источник истины — свежий main.
> Прочитай AGENTS.md, README.md и документы нужной области. Задача: [что изменить].
> Критерий результата: [что пользователь должен увидеть или получить].
> Сохрани действующие контракты проекта, кроме явно указанных изменений.
> Внеси правки, проверь соответствующее поведение и Chromium/WebKit CI,
> затем выпусти проверенную версию. В отчёте покажи изменения, проверки,
> размер до/после и количество добавленных/удалённых файлов.

## Как задавать конкретную задачу

| Задача | Что добавить в промпт |
| --- | --- |
| Внешний вид | Название экрана/компонента, нужный размер экрана, светлая/тёмная тема, точное визуальное изменение. При необходимости приложите референс. |
| Ошибка | Шаги воспроизведения, ожидаемое и фактическое поведение, браузер/устройство, обычная вкладка или установленная PWA. |
| Производительность | Наблюдаемая задержка и сценарий. Попросите измерить работу до/после и сохранить поведение таймера. |
| Навигация | Исходная и конечная страницы, действие пользователя, поведение кнопок назад/вперёд, необходимость сохранить состояние. |
| Данные | Что должно сохраниться при перезагрузке/импорте/ошибке записи; какие данные можно изменять. |

### Пример: дизайн

> На Home в мобильной тёмной теме сделай вторичный текст карточки активности
> заметнее. Измени только контраст текста. Проверь компактный экран, обычный
> iPhone и широкую версию, а также светлую тему. Обнови только визуальные
> эталоны, соответствующие согласованному изменению, после просмотра diff.

### Пример: исправление

> В установленной PWA: запускаю утренний таймер, сворачиваю приложение на
> 20 секунд и возвращаюсь. Ожидаю правильное оставшееся время и сохранённый
> прогресс. Найди причину [описание фактической ошибки], добавь регрессию,
> сохрани endAt и учёт активного времени, проверь и выпусти исправление.

### Пример: оптимизация

> Оптимизируй [компонент или сценарий] без изменения интерфейса. Сначала
> измерь [размер / DOM-обновления / число запросов], затем измени код и
> сравни те же метрики. Не подменяй успешный Swup-переход полной перезагрузкой
> и не принимай новые визуальные эталоны ради зелёных тестов.

## Где менять код

Home — app.js; история и импорт/экспорт — progress.js; данные — state.js;
представление упражнения — session-view.js; таймер/rest/completion — session.js;
общие интерфейсные примитивы и отмена задач страницы — ui.js; переходы —
navigation.js; sheets/GSAP — motion.js; PWA — pwa.js и sw.js; стили — styles.css.

## Проверки

`npm run check` проверяет целостность. `npm run test:e2e` запускает все сценарии
Chromium и WebKit. Можно сначала запустить нужный spec через
`npx playwright test tests/[имя].spec.js`, затем полный CI перед выпуском.

Визуальные эталоны — PNG в tests/visual-baselines: два браузера, компактная и
широкая геометрия, темы, settings, pause, rest и completion. При падении CI
приложит expected/actual/diff. Для нового согласованного дизайна захват эталонов
требует отдельного reference server и явных DM_CAPTURE_BASELINES=1 и
DM_BASELINE_URL; автоматическое принятие текущего сломанного UI запрещено.

Лучше один проверяемый результат на задачу. Если нужен пакет изменений,
перечислите отдельные критерии для каждого пункта и общие ограничения.
